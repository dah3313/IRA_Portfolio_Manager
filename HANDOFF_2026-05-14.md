## What landed today

### 1. Issue #4 fix — FBCG zero-quantity SELL halt resolved

**Two related bugs in `sgov_refill.py`, both fixed:**

**Bug A (latent):** `decide_buffer_refill` classified any Growth position with `cur_v > target_v` as "overweight" with no meaningful-drift floor. A position overweight by pennies could receive a near-zero refill allocation, producing a SourceLine that rounded to zero shares at the action layer.

**Bug B (the actual 2005-05-04 producer):** When the buffer deficit was a few cents (SGOV intraday price drift relative to target), the proportional-fallback split would produce sub-cent SourceLines for each Growth position, same halt class.

**The fixes:**
- A meaningful-drift gate on overweight detection: a position counts as overweight only when its surplus ≥ `core_total * rebalance_absolute_threshold_rate` (the same 5% drift yardstick the 5/25 rebalancer uses). Reuses an existing ruleset rate; no new tunable.
- A noise-floor gate on the buffer deficit itself: refill is planned only when `deficit ≥ buffer_target_dollars * 0.02` (2% of target). Below this, the deficit is sub-meaningful drift and no refill batch is planned. The 2% is hardcoded, scales with `buffer_target` (which scales with CPI), and is comfortably below the monthly refill rate of ~8.3% of target.

**Verification:** 11/11 unit tests pass in `test_sgov_refill_meaningful_drift.py`. The 20-year baseline scenario runs end-to-end with zero halts and all expectations passing. Terminal AUM moved from $3,304,555.43 (pre-fix, with the one halt absorbed) to $3,304,781.68 (post-fix), a $226 difference reflecting the previously-failed trades now succeeding and compounding over 20 years.

**Files touched:**

### 2. Architectural decisions made

The conversation evolved through a substantial design discussion. Key decisions:

**IRAPM is system of record (α architecture).** IRAPM produces its own authoritative event log. IBKR is a counterparty, not a database. All reports, audits, reconciliations are pure functions of the IRAPM event log.

**Two new file types replace the current scattered logging:**
- `events.jsonl` — single append-only event log capturing everything IRAPM does
- Text reports (operator-facing) — rendered by a reporter that consumes the event log

**The current 12-file IPMS output package is dead.** It will be deleted in Phase 2 of the migration; the new reporter replaces it entirely. The decision was option B (clean replacement) over option A (parallel-then-delete).

**The slave box does not depend on the event log.** Slave-promotion reconstructs order state from IBKR directly. The event log is operator-facing infrastructure (via the reporter) and forensic-grade record, not on the runtime critical path. Replication of the event log to the slave box is desirable but not load-bearing.

**Retention model:**
- `events.jsonl`: append-only forever, single file, no pruning, no compression. At ~500 KB/year, 30 years is ~15 MB — trivial.
- Year files (`{YYYY}.txt`): 8 years rolling retention.

**Report format:** Fixed-width plain text. Annual section on top, monthly section below. Annotations on separate lines below their data row to keep data-row alignment clean.

A concise (not full-spec) record of the report design. Documents:

- Reporter module API (`report.py`)
- When the reporter runs (weekly cycle invocations, monthly append on first cycle of next month, year-close on first cycle of new January, prune at year boundary)
- Format conventions (UTF-8, fixed-width, comma-separated thousands, mechanical column-width computation)

The file lifecycle is the most important part to understand:
- `current_status.txt` overwrites every weekly cycle
- `{YYYY}.txt` accumulates one row per month, monthly row is appended on the first weekly cycle of the *following* month (this lets each row reflect complete monthly aggregates)
- Year file closes on the first weekly cycle of the new year (December row + annual summary appended)
- 8-year rolling retention on year files

### Implementation phases (in order)

**Phase 1: Build the event log writer.**

1. Implement `event_log.py` at the repo root per EVENT_LOG_SPEC §5

   - `action_layer.py`: `fill_received` after order reaches FILLED status (iterate `OrderResult.fills`)

   - `action_layer.py`: `phase_transition` from `_execute_phase_transition`

3. Unit tests for the writer module (round-trip, Decimal preservation, timezone enforcement, concurrent-read tolerance, disk-failure handling).

4. Verify: run the baseline scenario. The `events.jsonl` should be populated with plausible events. Existing tests still pass.

**Phase 2: Build the reporter.**

1. Implement `report.py` per REPORT_DECISIONS.md

3. Tests against synthetic event logs (fabricated JSONL strings, not real runs)
4. Wire the reporter into cycle.py:
   - Every weekly cycle: call `write_current_status()`
   - First weekly cycle of each month: call `append_monthly_row_to_year_file()` for prior month

**Phase 3: Delete the old IPMS output package.**

## Important things to NOT do in the next session

1. **Don't make changes to cycle.jsonl or cb_transitions.jsonl's record schemas.** They are frozen in capability per the migration plan in EVENT_LOG_SPEC §7.6. If something new needs logging, it goes in the event log, never the legacy files.

2. **Don't try to make IPMS into the reporter.** That architectural pivot was explicitly rejected. IPMS becomes pure price-feed + simulator after Phase 3; reporting is IRAPM's responsibility via `report.py`.

3. **Don't add cash_settled as an event type.** It was deliberately dropped — settlement is observable via portfolio_snapshot deltas.

4. **Don't add fsync batching, indexes, or other performance optimizations** to the event log writer in Phase 1. Performance at our scales (50K events / 15 MB / 30 years) doesn't warrant them. Premature optimization adds complexity for no benefit.

5. **Don't introduce new event types beyond the 13 already cataloged in Section 4** unless an implementation discovery shows one of the existing types is insufficient. The catalog is the contract; expanding it requires a spec update first.

6. **Don't try to write a single huge change in one shot.** Phases 1 and 2 are large enough to warrant breaking down into stages: writer → emission sites → tests → reporter → integration. Stop at each stage for verification.
